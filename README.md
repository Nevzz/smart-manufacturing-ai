# Smart Manufacturing AI

**Predictive Maintenance & Visual Quality Inspection**
MBA (Digital Transformation) — Machine Learning for Data-driven Decision Making

A single Streamlit application with four analytics modules built on real
manufacturing data.

| # | Module | Technique | Status |
|---|--------|-----------|--------|
| 1 | Predictive Maintenance | Logistic Regression vs Decision Tree vs Random Forest | Trained ✓ |
| 2 | Machine Segmentation | K-Means + PCA | Trained ✓ |
| 3 | Defect Detection | ResNet-50 (ImageNet, frozen backbone) | Run locally |
| 4 | Maintenance Assistant | RAG: LangChain + ChromaDB + LLM | Run locally |

**Stack:** Python · scikit-learn · TensorFlow/Keras · LangChain · ChromaDB ·
PostgreSQL · Streamlit · Plotly · MLflow

## 1. Results so far

### Module 1 — Predictive Maintenance

Trained on 8,000 rows, evaluated on a stratified 2,000-row test set.

| Model | Accuracy | Precision | Recall | F1 | ROC-AUC |
|---|---|---|---|---|---|
| Logistic Regression | 0.858 | 0.178 | 0.882 | 0.296 | 0.939 |
| Decision Tree | 0.943 | 0.366 | 0.926 | 0.525 | 0.951 |
| **Random Forest** | **0.993** | **0.965** | 0.809 | **0.880** | **0.983** |

A model that always predicts "no failure" scores **0.966 accuracy** and catches
nothing. That baseline is why this comparison is judged on recall, F1 and
ROC-AUC rather than accuracy.

The interesting finding is not that Random Forest wins. It is the trade-off
Logistic Regression makes: it catches the most failures (88.2% recall) but
produces 277 false alarms against 60 true catches. High recall bought with
unusable precision is not a deployable model — every false alarm costs
inspection hours.

**Top factors affecting machine failure** (Random Forest):

| Factor | Importance |
|---|---|
| Rotational speed (rpm) | 22.1% |
| Torque (Nm) | 18.7% |
| Mechanical power (W) | 18.2% |
| Tool wear (min) | 14.4% |
| Wear × torque | 10.9% |

Three of the top five are set by the operator, not by the machine. A meaningful
share of failures is addressable through parameter discipline and tool-change
policy rather than capital spend.

### Module 2 — Machine Segmentation

Four operating regimes, k chosen for interpretability and risk separation.

| Cluster | Segment | Records | Failure rate |
|---|---|---|---|
| 1 | Worn tooling | 2,384 | **5.70%** |
| 2 | Fresh tooling | 2,368 | 3.80% |
| 3 | High-speed operation | 1,713 | 2.39% |
| 0 | Heavy-load operation | 3,535 | 2.04% |

Plant average is 3.39%, so the worn-tooling regime carries roughly 1.7× the
average risk. PCA retains 75.0% of variance across two components (PC1 38.2%,
PC2 36.8%).

**State this honestly in the report:** silhouette scores sit at 0.22–0.26 across
k = 2 to 8 with no elbow in the inertia curve. The sensor readings form one
continuous cloud, not naturally distinct populations. The clusters are a useful
way of organising operating conditions — justified by the failure-rate spread
between them — not evidence of separate machine types.

## 2. Dataset notes

### AI4I 2020 Predictive Maintenance
10,000 rows × 14 columns, zero missing values. 339 failures (3.39%).

**Target leakage was the critical issue.** `Machine failure` is effectively the
OR of the five failure-mode flags (TWF, HDF, PWF, OSF, RNF) — they disagree on
only 27 of 10,000 rows. Leaving those flags in as features makes every model
score ~100% and the comparison meaningless. All five are dropped, along with
`UDI` and `Product ID`.

Three engineered features were added, each corresponding to how a failure mode
is physically defined:

| Feature | Formula | Relates to |
|---|---|---|
| `temp_diff_k` | process − air temperature | Heat dissipation failure |
| `power_w` | torque × rotational speed × 2π/60 | Power failure |
| `wear_torque` | tool wear × torque | Overstrain failure |

Failure rate by product quality variant: L 3.92%, M 2.77%, H 2.09%.

### NEU Surface Defect (NEU-CLS)
1,800 BMP images, 200×200, grayscale, 6 classes at exactly 300 each.

The class is encoded in the filename (`Cr_1.bmp`), not in folders, so
`prepare_data.py` reorganises them into `train/` and `val/` class folders with
an 80/20 stratified split (240/60 per class).

| Prefix | Defect |
|---|---|
| Cr | Crazing |
| In | Inclusion |
| Pa | Patches |
| PS | Pitted Surface |
| RS | Rolled-in Scale |
| Sc | Scratches |

ResNet-50 expects 3-channel 224×224 input, so the grayscale images are resized
and channel-repeated at load time.

## 4. Setup

### Prerequisites
- Python 3.10, 3.11 or 3.12
- PostgreSQL 14+ *(optional — see note below)*
- An Anthropic or Google API key for module 4 *(optional)*

### Install

```bash
cd smart-manufacturing-ai

python -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate

pip install -r requirements.txt
```

### Place the datasets

```bash
mkdir -p data/raw
unzip ai4i_2020_predictive_maintenance_dataset.zip -d data/raw/

# NEU-CLS.rar — Windows: right-click → extract into data/raw/
# macOS/Linux:
unrar x NEU-CLS.rar data/raw/      # or: bsdtar -xf NEU-CLS.rar -C data/raw/
```

You should have `data/raw/ai4i2020.csv` and `data/raw/NEU-CLS/` with 1,800 BMPs.

### Configure

```bash
cp .env.example .env
```

Edit `.env` and fill in whatever you have. Every value is optional — see below.

**PostgreSQL is optional.** Every script tries the database and falls back to
CSV files in `data/processed/` if it isn't reachable, printing a one-line
notice. Your demo won't break if Postgres is down. To use it:

```sql
CREATE DATABASE smart_manufacturing;
```

Tables `sensor_readings` and `machine_segments` are created automatically.

**The LLM key is optional.** Without one, module 4 runs in retrieval-only mode:
it still searches the knowledge base and shows the relevant manual passages, it
just doesn't write a natural-language answer on top.

## 5. Running the project

Steps 1–5 are one-time. After that, only step 6.

```bash
# 1. Clean the CSV, engineer features, split images, load into PostgreSQL
python src/prepare_data.py

# 2. Train and compare the three classifiers          (~30 seconds)
python src/train_maintenance.py

# 3. K-Means segmentation + PCA                       (~20 seconds)
python src/train_segmentation.py

# 4. Fine-tune ResNet-50 on defect images             (10-20 min on CPU)
python src/train_vision.py

# 5. Build the ChromaDB knowledge base                (~1 min first run)
python src/build_rag.py

# 6. Launch the app
streamlit run app/main.py
```

The app opens at `http://localhost:8501`. The home page shows a status panel
telling you which steps have been completed and which command to run next, so
you can't get lost.

**First run of steps 4 and 5 downloads models** — ResNet-50 ImageNet weights
(~100 MB) and the FastEmbed embedding model (~130 MB). Both cache afterwards.
You need an internet connection for these two steps only.

### MLflow

```bash
mlflow ui --backend-store-uri sqlite:///mlflow.db
```

Open `http://localhost:5000`. Note the `--backend-store-uri` flag: current
MLflow versions refuse the old `./mlruns` file backend outright, so this project
uses SQLite. Running plain `mlflow ui` will not find your runs.

## 6. Implementation decisions worth defending

**`class_weight='balanced'` on all three models.** Without it, every model
collapses to predicting "no failure". With it, the models pay attention to the
3.4% minority class. This single parameter is what makes the comparison
meaningful.

**Permutation importance for Logistic Regression.** Tree models expose
`feature_importances_` directly; logistic regression doesn't. Permutation
importance (scored on ROC-AUC) puts all three models on a comparable footing
rather than mixing coefficient magnitudes with Gini importance.

**Frozen ResNet-50 backbone.** With 1,800 images across six classes, training
all ~25M parameters would memorise the training set. Only the classification
head trains.

**FastEmbed instead of sentence-transformers.** FastEmbed runs on ONNX Runtime,
so you avoid installing PyTorch alongside TensorFlow — roughly 2 GB saved and
one less framework conflict.

**Six maintenance documents were written for the RAG knowledge base**, grounded
in the actual AI4I threshold definitions (the 8.6 K temperature difference, the
3,500–9,000 W power band, the variant-specific overstrain limits). This means
the chatbot's advice lines up with what the predictive model is flagging, rather
than being generic text. Replace them with real documents if you have them.

## 7. Suggested demo order

1. **Home** — point at the 3.39% failure rate and the 96.6% baseline. Frame the
   problem before showing any model.
2. **Predictive Maintenance → Model comparison** — the dashed baseline line on
   the metric chart does the explaining for you.

4. **Machine Segmentation → Segment profiles** — the failure-rate bar chart

   shows the true label so correctness is visible.

   do?" and open the Sources expander to show it isn't hallucinating.

## 8. Troubleshooting

| Problem | Fix |
|---|---|
| All three models score ~100% | The leakage flags weren't dropped — check `config.LEAKAGE_COLS` |
| Recall is 0 despite 96.6% accuracy | `class_weight='balanced'` is missing |
| `mlflow ui` shows no experiments | Add `--backend-store-uri sqlite:///mlflow.db` |
| MLflow raises a "maintenance mode" error | You're on a file store URI; this project uses SQLite |
| `psycopg2` fails to install | Use `psycopg2-binary` (already in requirements.txt) |
| "PostgreSQL unavailable" in script output | Expected and harmless — it fell back to CSV |
| ResNet training is very slow | Normal on CPU. Reduce `EPOCHS` in `config.py` to 3 |
| Streamlit page says "not trained yet" | Run the command shown on that page |
| Module 4 gives retrieval-only answers | No API key in `.env` — add `ANTHROPIC_API_KEY` |
| Image folders not found | Run `python src/prepare_data.py` first |
